RaceDay is a South African road-event platform for running, walking and cycling events. This repo contains the Part 2 API: an ASP.NET Core Web API (.NET 8) that handles users, events, categories, enrolments and results, with role-based access for **Organisers** and **Participants**.

## Tech stack

- ASP.NET Core Web API (.NET 8, C#)
- Entity Framework Core 8, **Code-First**, SQL Server
- Cookie-based session authentication with role claims
- BCrypt password hashing
- Swagger (Swashbuckle) for live endpoint documentation
- xUnit tests (in-memory database) and GitHub Actions CI

## Running the project

1. **Clone** the repo and open `RaceDay.api.sln` in Visual Studio 2022.
2. In `RaceDay.api/appsettings.json`, set the connection string to your own SQL Server instance:
```json
   "DefaultConnection": "Server=YOUR_SERVER\\SQLEXPRESS;Database=RaceDayDB;Trusted_Connection=True;TrustServerCertificate=True;"
```
3. Create an empty database called `RaceDayDB` in SSMS.
4. In **Package Manager Console** (default project `RaceDay.api`), run:
```
   Update-Database
```
   This builds all tables from the EF Core models and migrations.
5. Run the project. Swagger opens at `https://localhost:<port>/swagger`.

## Authentication and roles

- `POST /api/Auth/register` creates an account with the role `organiser` or `participant`.
- `POST /api/Auth/login` starts a cookie session that carries the user's identity and role on every later request.
- Passwords are hashed with BCrypt, and the plain text is never stored.
- All endpoints except register and login require a logged-in user. Role-restricted endpoints return **403** for the wrong role and **401** when not logged in.
- Organisers can only change or view enrolments and results for **their own** events.

In Swagger, call **login** first. The browser keeps the session cookie, so later calls are authenticated.

## Endpoints

| Method | Route | Role | Purpose |
|---|---|---|---|
| POST | `/api/Auth/register` | Public | Register as organiser or participant |
| POST | `/api/Auth/login` | Public | Log in and start a session |
| POST | `/api/Auth/logout` | Any | End the session |
| GET | `/api/Profile` | Both | View own details and profile |
| PUT | `/api/Profile` | Both | Create or update own profile |
| GET | `/api/Events` | Both | List all events |
| GET | `/api/Events/{id}` | Both | View one event |
| POST | `/api/Events` | Organiser | Create an event |
| PUT | `/api/Events/{id}` | Organiser (owner) | Update own event |
| DELETE | `/api/Events/{id}` | Organiser (owner) | Delete own event |
| GET | `/api/events/{eventId}/categories` | Both | List an event's categories |
| POST | `/api/events/{eventId}/categories` | Organiser (owner) | Add a category to own event |
| PUT | `/api/categories/{id}` | Organiser (owner) | Update a category |
| DELETE | `/api/categories/{id}` | Organiser (owner) | Delete a category |
| POST | `/api/categories/{categoryId}/enrol` | Participant | Enrol in a category (links participant, event and category) |
| GET | `/api/enrolments/my` | Participant | View own enrolments |
| GET | `/api/events/{eventId}/enrolments` | Organiser (owner) | View all enrolments for own event |
| POST | `/api/enrolments/{enrolmentId}/result` | Organiser (owner) | Capture finish time and positions |
| PUT | `/api/results/{id}` | Organiser (owner) | Correct a result |
| GET | `/api/events/{eventId}/results` | Organiser (owner) | View results for own event |
| GET | `/api/results/my` | Participant | View own results |

Every endpoint is documented in Swagger with its purpose, expected data and possible responses.

## Tests

Unit tests are in `RaceDay.Tests` and run against an in-memory database, so they never touch SQL Server. They cover success and failure cases for:

- Registration and login (valid, duplicate email, invalid role, wrong password, unknown user)
- Unauthenticated requests being rejected (401)
- Event management by organisers, including blocking other organisers from editing someone else's event
- Wrong-role access being rejected (403), such as a participant creating an event or an organiser enrolling
- Enrolment being recorded correctly and visible to both participant and organiser
- Result capture by organisers and viewing by participants

Run them in Visual Studio (Test Explorer → Run All) or with:

```
dotnet test
```

## CI/CD

GitHub Actions (`.github/workflows/ci.yml`) restores, builds and runs the unit tests on every push and pull request to the main branch.

## Differences from the Part 1 ERD and SQL script

The schema is now generated by EF Core (Code-First), so a few things differ from the hand-written Part 1 script:

1. **`Events.DistanceKM` was added.** The Part 2 brief requires each event to capture a distance, and the Part 1 ERD only stored distance on `Categories`.
2. **Value rules are enforced in the API, not by SQL CHECK constraints.** Role (`organiser`/`participant`), event type (`run`/`walk`/`cycle`), enrolment status and payment status are validated in the controllers, and defaults such as `'pending'` and `'unpaid'` are set in the C# models.
3. **Cascade rules.** `Events.OrganiserID` and `Enrolments.UserID` use `Restrict` (no cascade delete) to avoid SQL Server's "multiple cascade paths" error. Other relationships cascade.
4. **Indexes.** Unique indexes enforce one profile per user, one result per enrolment, a unique email, and one enrolment per user per category.
